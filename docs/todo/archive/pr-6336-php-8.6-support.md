## 3. What the PR actually changes

Two distinct kinds of edit, which should be judged separately.

### 3a. Null-to-string guards — worth taking

The recurring pattern, from [DB_query_builder.php](system/database/DB_query_builder.php):

```php
- $val = trim($val);
+ $val = trim((string)$val);
```

```php
- $alias = $this->_create_alias_from_table(trim($select));
+ $alias = $this->_create_alias_from_table(trim((string)$select));
```

These apply cleanly. The corresponding sites in this fork are
[DB_query_builder.php:304](system/database/DB_query_builder.php#L304),
[DB_query_builder.php:418](system/database/DB_query_builder.php#L418) and
[DB_query_builder.php:421](system/database/DB_query_builder.php#L421), all still uncast.
A count of `trim((string)` occurrences in that file returns zero, so none of this work
has been done here.

### 3b. Property visibility widening — should not be taken

```php
- protected $qb_select   = array();
+ public    $qb_select   = array();
```

```php
- protected $qb_orderby  = array();
+ public    $qb_orderby  = array();
```

Current state in this fork:
[DB_query_builder.php:74](system/database/DB_query_builder.php#L74) and
[DB_query_builder.php:144](system/database/DB_query_builder.php#L144), both still
`protected`.

This has no bearing on PHP 8.6 compatibility. Widening a property from `protected` to
`public` is a one-way contract change: once published it cannot be narrowed again
without breaking any consumer that came to rely on it. No justification for it appears
in the PR. It should be dropped from any port.

## 4. Relevance to PHP 8.6 specifically

The deprecation these casts address — passing `null` to a non-nullable parameter of an
internal function — was introduced in **PHP 8.1**, not 8.6. Nothing in the examined
portion of the diff is specific to 8.6.

Two consequences:

- The changes are not urgent for an 8.6 move. Code that runs clean on 8.5 will not newly
  emit these notices on 8.6.
- The notices are **data-dependent, not load-time**. They fire only when a `null`
  actually reaches one of the call sites, so their absence in a running application is
  not evidence that the call sites are safe.

This repository's [readme.rst:25](readme.rst#L25) currently states "PHP version 7.4 or
newer is recommended (PHP 8.5 ready)." That line is the natural place to record an 8.6
claim, and should not be updated until such a claim is actually substantiated.

## 5. Backward compatibility

- **Section 3a (casts):** additive and behaviour-preserving for all non-null inputs. For
  null inputs the observable change is the suppression of a deprecation notice;
  `trim(null)` and `trim((string)null)` both yield `''`.
- **Section 3b (visibility):** a contract change, as described above.
- **Section 2 (whole-file additions):** a regression if applied to this fork.

## 8. Effort and scope options

| Option | Scope | Effort | Risk |

## 9. Recommendation

1. **(a) or (b).** There is no demonstrated 8.6 blocker, so deferring is defensible. If
   action is preferred, take (b): the casts at
   [DB_query_builder.php:304](system/database/DB_query_builder.php#L304),
   [:418](system/database/DB_query_builder.php#L418) and
   [:421](system/database/DB_query_builder.php#L421) are cheap, additive, and covered by
   the configured `mysqli` driver.
2. **Exclude unconditionally** from any port: the four whole-file additions in section 2,
   and the visibility changes in section 3b.
3. **Deferred:** the remaining ~70 files, the workflow changes, and the test changes,
   none of which were examined. Enumerating them is a separate piece of work and should
   not be assumed to be covered by this document.
4. **Do not update** [readme.rst:25](readme.rst#L25) to claim 8.6 readiness on the
   strength of this PR.
